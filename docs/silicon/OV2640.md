# OmniVision OV2640 (2 MP UXGA CMOS Sensor) — Silicon Reference

Ground-truth silicon reference for the **OmniVision OV2640** camera sensor used on the **AI-Thinker ESP32-CAM**, focused on getting maximum frame rate, image quality, reliability, and low latency in BalaX's thin-robot architecture.

---

## 1. Sensor Array, Optics & Physical Limits

| Parameter | Datasheet Spec | Practical Meaning for BalaX |
| :--- | :--- | :--- |
| **Optical Format** | 1/4-inch CMOS | Standard M12/mini lenses (typically ~65° normal or ~120°–160° wide-angle fisheye) |
| **Array Size** | `1632 × 1232` total / **`1600 × 1200` active (UXGA, 2.0 MP)** | Native 4:3 aspect ratio |
| **Pixel Pitch** | `2.2 µm × 2.2 µm` (OmniPixel2, Bayer CFA) | Small pixels → needs decent indoor light; high gain gets noisy quickly |
| **Sensitivity / SNR / DR** | `0.6 V/Lux-s`, `40 dB` SNR, `50 dB` dynamic range | Modest dynamic range; bright windows blow out unless AE/exposure is tuned |
| **Shutter & Scan** | **Electronic Rolling Shutter**, progressive scan | Lines expose sequentially (top to bottom) — **causes jello/skew during robot pitch oscillation & vibration!** |
| **Max Exposure Interval** | `1247 × tROW` | Long indoor exposures blur balancing motion; prefer higher gain + capped shutter for vision |
| **Voltage Rails** | `DVDD = 1.3 V ± 5%` (1.2 V LDO on AI-Thinker), `AVDD = 2.5–3.0 V` (2.8 V LDO), `DOVDD = 1.7–3.3 V` (3.3 V) | All rails gated on AI-Thinker by `GPIO 32` (`LOW` = ON) |
| **Active Power** | **125 mW** (YUV) / **140 mW** (JPEG) @ UXGA 15 fps | Continuous streaming heats the tiny camera PCB significantly |
| **Standby Current** | **600 µA** (software/PWDN standby) | Even better on AI-Thinker: `GPIO 32 = HIGH` cuts the LDOs to ~0 mA |
| **Stable Image Temp** | **`0 °C – 50 °C`** | Above ~50 °C die temp, dark current / color noise rises noticeably in dim rooms |

## 2. SCCB Control Bus & Dual-Bank Register Architecture

The OV2640 is configured over **SCCB** (OmniVision's I²C-like 2-wire bus on `GPIO 26` SIOD / `GPIO 27` SIOC on AI-Thinker).

### 2.1 Critical SCCB Quirks
- **Device address:** 7-bit **`0x30`** (8-bit write `0x60`, read `0x61`), max clock **400 kHz** (`100 kHz` is safest on long flex ribbons).
- **`XCLK` MUST be running first!** The OV2640 internal logic is clocked by `XCLK` (`GPIO 0`). If `XCLK` is stopped or `GPIO 32` (`PWDN`) is HIGH, every SCCB transaction will NACK (`ESP_ERR_NOT_FOUND` / `Camera probe failed`).
- **No I²C repeated-START on read:** Strict SCCB expects a **STOP** condition between the 2-phase register-address write and the 2-phase read (`esp32-camera`'s SCCB driver handles this; custom I²C code using `i2c_master_transmit_receive` with repeated-START can fail on some OV2640 dies!).

### 2.2 Bank Switching (`0xFF` — `RA_DLMT`)
Every register address is overloaded across **two banks** selected by writing register **`0xFF`**:
- **`0xFF = 0x00` → DSP Bank** (JPEG quantization `QS`, output format, cropping/zoom/downscaling, AEC/AWB/gamma/LENC/BPC/effects).
- **`0xFF = 0x01` → Sensor Bank** (chip ID `PIDH`/`PIDL`, `CLKRC` prescaler, timing/blanking, analog gain, manual exposure, mirror/flip).

### 2.3 Key Registers to Know
| Bank (`0xFF`) | Addr | Name | Default / Expected | Purpose |
| :---: | :---: | :--- | :---: | :--- |
| `0x01` (Sensor) | `0x0A` | `PIDH` | **`0x26`** | Product ID high byte (read-only) |
| `0x01` (Sensor) | `0x0B` | `PIDL` | **`0x42`** (or `0x41`/`0x40`) | Product ID low / silicon rev (accept `0x40–0x42`) |
| `0x01` (Sensor) | `0x1C` / `0x1D` | `MIDH` / `MIDL` | `0x7F` / `0xA2` | OmniVision Manufacturer ID |
| `0x01` (Sensor) | `0x11` | `CLKRC` | — | Internal clock prescaler (`bit[7]` = PLL double; `bits[5:0]` = divider) |
| `0x01` (Sensor) | `0x12` | `COM7` | — | Soft reset (`bit[7]`), sensor readout mode (`UXGA` / `SVGA` / `CIF`) |
| `0x01` (Sensor) | `0x13` | `COM8` | — | Auto Gain (`AGC`, bit 2) & Auto Exposure (`AEC`, bit 0) enable |
| `0x01` (Sensor) | `0x00` | `GAIN` | — | Manual AGC gain (`0–30` in `esp32-camera`) |
| `0x01` (Sensor) | `0x04` | `REG04` | — | Horizontal mirror & vertical flip (`hmirror` / `vflip`) |
| `0x00` (DSP) | `0x44` | **`QS`** | **`0x0C` (12)** | **JPEG Quantization Scale (`0–63`; LOWER = higher quality & larger bytes!)** |
| `0x00` (DSP) | `0xDA` | `IMAGE_MODE` | — | Output pixel format (`JPEG`, `RGB565`, `YUV422`) |
| `0x00` (DSP) | `0xD3` | `R_DVP_SP` | — | DVP PCLK speed divider |
| `0x00` (DSP) | `0xC2` / `0xC3` | `CTRL0` / `CTRL1` | — | DSP pipeline module enables (AWB, gamma, LENC, BPC, WPC, CIP) |

## 3. On-Chip DSP & Hardware JPEG Engine (The OV2640 Superpower)

Unlike raw-only sensors (e.g., OV7670) that choke an ESP32 with uncompressed pixels, the OV2640 contains a **dedicated hardware ISP + JPEG encoder** inside the sensor silicon:
- **Zero ESP32 CPU encoding cost:** The OV2640 outputs complete, valid **JFIF/JPEG byte streams (`FFD8 ... FFD9`)** directly over the 8-bit DVP parallel bus into PSRAM via DMA.
- **Massive bandwidth reduction:** A `VGA (640×480)` RGB565 frame is `614 KB` (impossible at 30 fps over ESP32 Wi-Fi + I²S0), whereas a `VGA` hardware JPEG at `QS = 12` is typically **`15–35 KB`** — a ~20–30× reduction!

### 3.1 JPEG Quality (`QS` Register `0x44`) Rules
- **Inverse scale:** `0`–`63` (values > 63 wrap!). **Lower number = higher quality = larger frame**.
- **Sweet spot:** **`QS = 10–16`** for FPV/vision streaming; **`QS = 8–10`** for high-detail stills.
- **Danger zone (`QS < 6` at SVGA/UXGA):** High-texture scenes can burst past the pre-allocated PSRAM JPEG buffer size, causing truncated/corrupt frames or DMA buffer overflows (`esp32-camera` sizes buffers heuristically from resolution + quality).

## 4. Clocking Tree (`XCLK` → PLL → `PCLK`) & ESP32 DMA Limits

```
ESP32 LEDC (GPIO 0) ──▶ XCLK (6–24 MHz) ──▶ OV2640 PLL & CLKRC ──▶ Sensor Core & DSP ──▶ PCLK (out on GPIO 22)
```

- **Datasheet `XCLK` range:** **6 MHz – 24 MHz** (45–55% duty cycle).
- **Datasheet max `PCLK`:** Up to **36 MHz** (UXGA @ 15 fps).
- **ESP32 classic I²S0 DMA ceiling:** On ESP32-CAM with PSRAM + Wi-Fi running, **keep `PCLK ≤ ~16–20 MHz`** (typically achieved by setting `XCLK = 20 MHz` for QVGA–VGA, or lowering **`XCLK = 10–16 MHz`** for SVGA/UXGA or noisy flex cables).
- **Symptom of too-fast `XCLK`/`PCLK`:** `EV-VSYNC-OVF`, `FB-OVF`, green/magenta horizontal tears in JPEG output, or `cam_hal: Failed to get the frame on time!`. First fix to try is lowering `xclk_freq_hz` from `20 MHz` to `16 MHz` or `12 MHz`.

## 5. Sensor Readout Modes, FOV & Resolution/FPS Matrix

The OV2640 has **three native hardware sensor readout modes** (`UXGA`, `SVGA`, `CIF`), and its on-chip DSP can crop or downscale from those modes down to `40 × 30`:

| Native Sensor Mode | Sensor Resolution | Hardware Max FPS | Typical Downscaled Outputs (`esp32-camera`) | Real-World ESP32-CAM Wi-Fi JPEG FPS | Typical JPEG Size (`QS=12`) |
| :--- | :---: | :---: | :--- | :---: | :---: |
| **UXGA** | `1600 × 1200` | 15 fps | `UXGA`, `SXGA (1280×1024)`, `HD (1280×720)`, `XGA (1024×768)` | 4–12 fps | 50–150 KB |
| **SVGA** | `800 × 600` | 30 fps | `SVGA`, **`VGA (640×480)`**, `HVGA (480×320)` | **15–25 fps** | 15–40 KB |
| **CIF** | `400 × 296` | 60 fps | `CIF`, **`QVGA (320×240)`**, `QQVGA (160×120)` | **25–50 fps** | 5–15 KB |

**Important FOV vs. FPS trap:**
- Switching from `SVGA` → `VGA` or `UXGA` → `HD` can **crop the field of view** instead of scaling the full sensor unless `set_res_raw()` / DSP scaling (`OUTW`/`OUTH`) is configured intentionally!
- Conversely, **SVGA/UXGA native readout + DSP crop** is a hidden superpower: you can shift the DSP crop window vertically (`Y` offset) using BalaX's 100 Hz pitch angle for **in-sensor electronic pitch stabilization** (or stream full `QVGA`/`VGA` and stabilize in `balax-remote`'s WebGL shader with zero camera latency).

## 6. ISP Tuning & Robotics Best Practices (BalaX Thin-Robot Policy)

### 6.1 Low-Latency FPV Configuration (`esp32-camera`)
- `pixel_format = PIXFORMAT_JPEG` (never stream RGB565/YUV over Wi-Fi).
- `frame_size = FRAMESIZE_QVGA` (320×240, lowest latency) or `FRAMESIZE_VGA` (640×480, crisp FPV).
- `jpeg_quality = 12` (10–16 range).
- `fb_count = 2` in PSRAM + **`grab_mode = CAMERA_GRAB_LATEST`** (prevents 1–2 frame stale FIFO lag that makes teleoperation feel sluggish!).
- `xclk_freq_hz = 16000000` (or `20000000` if zero `EV-VSYNC-OVF` in testing).

### 6.2 Fighting Rolling Shutter & Motion Blur on a Balancing Robot
- A self-balancing robot pitches continuously; in dim indoor light, default `AEC` stretches exposure time up to tens of milliseconds → heavy motion blur + rolling-shutter lean on vertical walls/AprilTags.
- **Robotics fixes:**
  1. Keep `aec2 = 1` (DSP night/auto-exposure) disabled when crisp low-latency motion matters; cap `ae_level` or switch to **manual exposure (`aec = 0`, `aec_value`) + moderate gain (`agc = 1` or manual `gainceiling`)** so shutter speed stays short (< 10–15 ms).
  2. Enable `bpc = 1` (black pixel cancel), `wpc = 1` (white pixel cancel), and `lenc = 1` (lens shading correction — especially important with wide-angle lenses!).
  3. Enable 50/60 Hz anti-banding under indoor LED/fluorescent lights to avoid rolling horizontal brightness bands.
  4. **Vibration isolation:** Mount the OV2640 ribbon and lens rigidly with foam damping — loose flex cables amplify rolling-shutter jello.

### 6.3 Thin-Robot Offload Pattern
Per [`../../AGENTS.md`](../../AGENTS.md):
- **On ESP32-CAM:** Only run hardware JPEG capture, minimal HTTP MJPEG/snapshot endpoint (`balax-cam.local`), MicroSD artifact/HIL logging, and UART RPC to BalaX.
- **In `balax-remote` (Browser TS/WebGL/WASM):** Perform all heavy vision & rendering — IMU-coupled electronic horizon stabilization, AprilTag/fiducial detection, optical flow, object tracking, and recording playback.
